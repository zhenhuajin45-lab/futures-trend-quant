## P1 修复与实际消费路径

1. **D27：已消费 INITIAL_CACHE 没有进入恢复前缀。**
   `INITIAL_CACHE → 原 seed + 严格 journal 恢复 → 同身份修订检查 → 合并后的实际窗口
   → 不可变 parquet/来源回执 → gm_input_cache → core_checkpoint.json`。
   重启先核对缓存哈希、实际合约、窗口和 journal，再检查已消费末端覆盖。
   旧缺失保护保留。五品种冻结原件重现旧二次启动失败，并验证新二次启动及显式迁移。
   原 runtime、last_eob、used_evidence_ids、Ordered B 状态、墓碑均保留。
   旧新首次回放只剔除真实评估时钟字段进行算法状态比较；迁移后的实际原状态逐字段完整比较。
   历史真实 known_at 缺失仍为 UNKNOWN。

2. **GM-02：预热中闭合回调被直接退回。**
   实际 SDK on_bar 适配后，未就绪时保留逐柱身份及原始 source/returned_at/run_id，
   附加本机捕获回执；CORE_READY 后限量进入原 ClosedM1Book，再进入 engine.m1/核心队列。
   修订、队列溢出拒绝；未交接尾部保留，不把无核心消费误写成供应商断线。

3. **GM-03/SCHED-01/EXEC-02：报价和结果交接积压。**
   GM Tick 使用按合约最新状态邮箱；备用轮询使用当前 run/config 绑定的独立原子文件。
   原 created_at 和 received_at 不重写；旧轮询不能替换新 Tick。
   仅报价可合并，闭合柱、候选、委托和 RPC 不合并。
   GM 先交接，组内轮转，GM/TQ 核心与行情预算独立；账户 RPC 在交接前后消费，风险检查继续执行。
   单轮工作仍有界；自然运行下的真实时延改善待新宿主及交易时段验收。

4. **CLOCK-01：降级探测等待过长。**
   retryable degraded 后下一次双源探测等待缩短至最多 5 秒。
   原始样本年龄、90 秒有效期、双源、偏差、源间差、RTT 与跳变检查均未放宽。
   网络持续丢包仍可停开；恢复健康不清除持久暂停。

5. **OBS-01/QA-01：运行健康与完整交易验证混淆。**
   状态单列 GM 实际核心存活、就绪、故障、工作进度和回调待处理数；
   Tick 到达、邮箱替换和实际应用数分别登记。
   实际 Windows `_signal_process` 连续两个新进程恢复同一冻结状态。
   原生 Py310 最终 submit 检查使用合成 SDK，不连接柜台，不造真实订单。

## 发布与剩余边界

- 安装必须重新证明用户正常停机、全部自有组件停止、空仓及无活动未知委托。
- 先备份全状态并哈希保护，再刷新真实只读账户证明，仍执行原有效期。
- 只迁移 execution/十个 pin 的配置身份，以及五个 GM 检查点新增的精确输入引用。
- 所有 pause/halt、授权历史、账本、候选、墓碑和退出保护保持原值。
- 可回滚包保留旧主文件、源码、私有配置及停机时状态。显式回滚只能在新宿主启动前，
  无新状态/委托/证据变化时执行；不得自动回滚或覆盖后来交易事实。
- TQ 原缺输入故障、未确认尾柱继续隔离/保留，未扩为本轮重点；PA 和背驰替代仍为 SHADOW。
- 持久暂停尚未解除。此前 R12 午盘授权不扩展为本版本的自动恢复授权。
- 用户随后真实启动及新 run/source 指纹、唯一控制器和自然交易闭环尚待实际验收。

## 复发预防

禁止把“内存已经消费”当作“重启输入已经持久化”。每次 INITIAL_CACHE 提交检查点前，
必须先生成绑定精确有效窗口的 gm_input_cache；缺失或哈希/合约/窗口改变即拒绝。
必须保留 old first boot → old second failure → new first/second success → legacy migration
的五品种原件回归，以及实际 spawn 重启、原截止和原生末端门槛验证。
